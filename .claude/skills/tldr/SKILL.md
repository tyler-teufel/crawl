# TLDR — Session Record

You are writing the durable record of a working session. The problem this solves: by the time work is done, the reasoning is spread across dozens of messages, several of which were superseded. Nobody will re-read that. This file is what they read instead.

Write for someone who was **not** in the session — a reviewer, or the user in three weeks. Assume they know the codebase and nothing about today.

## What this is not

- Not a transcript. Do not narrate turn by turn.
- Not a changelog. The diff already says what changed; this says **why**, and what it cost to get there.
- Not a status update. Past tense, settled facts.

## Non-negotiable content

These three survive any amount of compression. If the report gets long, cut narrative — never cut these.

**1. Decisions, and who made them.** For each: what was decided, **who decided it** (the user explicitly, or an assumption you proceeded on), and what was rejected. Mark assumptions clearly — an assumption the user never actually confirmed is the single most dangerous thing to lose, because later readers will treat it as settled.

**2. Reversals and corrections.** Anything you asserted that turned out wrong. Any work a review sent back, with what the reviewer found and what changed. Any approach abandoned mid-flight and why. This is the section people most need and least often get — write it even when it is unflattering, especially then.

**3. Open items, and who is blocked on what.** Split explicitly:
   - Needs the user (credentials, external console setup, a product call)
   - Needs a tool or access this session did not have
   - Deliberately deferred, with the reason and the condition that would revive it
   - Unverified — claimed done but not proven, and what proof is missing

## Gathering the facts

Do not reconstruct from memory alone; memory is what compaction erodes. Ground every claim:

- `git log <base>..HEAD --oneline` for what actually landed, and read the commit bodies — they carry the reasoning.
- `git status --porcelain` for anything still uncommitted, and say so.
- The PR's state and CI result if there is one.
- Ticket numbers for everything. A claim without a ticket or commit reference is a claim you should double-check before writing down.

If a subagent reported something you never independently verified, say so in those words. "The agent reported X" and "X is true" are different statements, and the difference matters more three weeks out than it does now.

## Structure

Adapt to the session — a one-ticket session does not need every heading. Order is deliberate: outcome first, reasoning next, unfinished business last.

```markdown
# <Date> — <short session title>

**Branch:** `<branch>` · **PR:** #N · **Tickets:** #A, #B, #C

## Outcome
Two or three sentences. What is now true that was not true before.

## Shipped
Per ticket: what changed, the commit, and how it was verified.
State verification honestly — "110 tests pass" and "an agent said it works"
are not the same claim.

## Decisions
| Decision | Made by | Alternatives rejected |
Mark unconfirmed assumptions explicitly.

## Reversals & corrections
What was wrong, what caught it, what changed.

## Open
Grouped by blocker: needs user / needs access / deferred / unverified.

## Next
The obvious next move, and anything that would change it.
```

## Output — both artifacts

**1. Commit a file** at `docs/sessions/YYYY-MM-DD-<short-slug>.md`. If a file for that date already exists, suffix the slug rather than overwriting — two sessions in a day are two records. Create `docs/sessions/` if absent.

**2. Post a condensed version** to the active PR as a comment: Outcome, Decisions, and Open only — reviewers need the reasoning and the blockers, not the full record. Link to the committed file for the rest. Skip this step if there is no open PR, and say so rather than inventing one.

Every GitHub comment ends with the attribution footer, per repo convention:

```
---
_Generated by [Claude Code](https://claude.ai/code)_
```

Commit the file with the session's normal git conventions. Do not push unless the branch is already pushed — match whatever the session has been doing.

## Calibration

Length follows the work. A single-ticket session might be 40 lines; a session that shipped five tickets through two rounds of review is longer, and padding it out or squeezing it down both make it worse.

Cut: restating diffs, praising the work, process narration ("then I dispatched..."), anything the reader can see in the PR.

Keep: the assumption nobody confirmed, the review finding that changed the approach, the thing that is still broken, the reason an obvious-looking option was rejected.

The test: hand it to someone who then asks "but why did you...?" — if that question is answered, the report worked.
