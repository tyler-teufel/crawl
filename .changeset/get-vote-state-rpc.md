#196: added `public.get_vote_state()`, a `SECURITY INVOKER` Postgres RPC that returns the caller's own vote state (`{ remainingVotes, maxVotes, votedVenueIds, resetAt }`) for the current vote day — the missing read-path counterpart to #126's `cast_vote` RPC. Fixes the beta's actual failure mode: with `EXPO_PUBLIC_API_URL` unset and Supabase configured, `useVoteState` falls through to device-local mock state while votes are written to Postgres, so a reinstall appears to reset the daily budget while the server still holds the real count, and the next cast is rejected with `NO_VOTES_REMAINING` against a UI claiming votes remain. `get_vote_state` runs `SECURITY INVOKER`, not `SECURITY DEFINER` like `cast_vote` — a read of the caller's own rows needs no elevated privilege, since `0002_rls_policies.sql`'s existing `"votes: read own"` policy already restricts it correctly. Also extracts `public.vote_max_daily_votes()` and `public.vote_reset_at(at, tz)` as shared helpers (both built on 0007's `public.vote_day()`) so the vote cap and the resetAt computation each have exactly one definition, and re-points `cast_vote` at them via `CREATE OR REPLACE` (0007 itself stays immutable) — no behavior change, same 26 existing `cast_vote` tests still pass. EXECUTE is revoked from `PUBLIC` and `anon`, granted only to `authenticated`; `auth.uid()` is the sole identity source, no user-id parameter. Shipped as `apps/api/drizzle/0008_get_vote_state_rpc.sql`, recorded in `apps/api/drizzle/meta/_journal.json` and `0008_snapshot.json` via `drizzle-kit generate --custom`. Verified against a scratch local Postgres 16 (zero-votes-today returns full budget, today's votes reflected in `remainingVotes`/`votedVenueIds`, a previous-vote-day row excluded, `resetAt` parity with `cast_vote` for the same instant, unauthenticated rejected with `AUTH_REQUIRED`, `anon` denied EXECUTE outright) — nothing applied to the live Supabase project (connector unauthorized this session). Extends the existing opt-in `apps/api/tests/db/cast-vote-rpc.test.ts` suite (gated on `TEST_DATABASE_URL`, now exercised in CI against a `postgres:16-alpine` service container as of the prior commit) rather than a sibling file, since a second file DROP/CREATEing the same unnamespaced `public.votes`/`venues`/`users` objects would race it under Vitest's default file-parallel execution. Mobile's read-branch fix (`apps/mobile/src/api/votes.ts`'s `useVoteState`, still gated on `hasApi` only) is out of scope here and reported back to the orchestrator as a follow-up.
