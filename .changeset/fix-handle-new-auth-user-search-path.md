#189: pinned `pg_temp` on `public.handle_new_auth_user()`'s `search_path` (`SET search_path = public, pg_temp`), matching the pattern `recalculate_hotspot_scores()` (0006), `cast_vote()`/`vote_day()` (0007), and `get_vote_state()`/`vote_max_daily_votes()`/`vote_reset_at()` (0008) already follow. `0005_users_provisioning_and_geo_remediation.sql` declared this `SECURITY DEFINER` trigger function with `SET search_path = public` only — Postgres always searches `pg_temp` first regardless of the declared `search_path`, so omitting it leaves the documented shadowing gap where a role with default TEMP privilege could create a session-local table that intercepts an unqualified reference inside a definer-privileged function. LOW severity, not a live hole today: the function's only table reference (`public.users`) is already schema-qualified, and Postgres refuses to invoke a `RETURNS trigger` function outside trigger context, so nothing shadows it and it can't be called directly as a PostgREST RPC either way — safe by how it happens to be written, not by its declaration. Closes the gap so a future edit adding an unqualified reference can't silently become exploitable. `0005` is an applied migration and stays immutable (verified with `git diff` — no changes); shipped as `apps/api/drizzle/0009_fix_handle_new_auth_user_search_path.sql` via `CREATE OR REPLACE FUNCTION` (identical signature: `handle_new_auth_user()`, `RETURNS trigger`, body copied verbatim, only the `search_path` line changes), recorded in `apps/api/drizzle/meta/_journal.json` and `0009_snapshot.json` via `drizzle-kit generate --custom`, same as 0007/0008's precedent. Also re-issues `REVOKE EXECUTE ON FUNCTION public.handle_new_auth_user() FROM PUBLIC` as belt-and-braces hardening (0005 never issued an explicit grant for this function, so it carried Postgres's default PUBLIC-EXECUTE the whole time — harmless since trigger invocation isn't subject to EXECUTE checks, but revoked anyway per the ticket). A grep of `apps/api/drizzle/**` confirms no other `SECURITY DEFINER` function still omits `pg_temp`. Nothing applied to the live Supabase project (no DB connector available this session; `0006`–`0008` are also still pending, so `0009` queues behind them) — verified statically against the sibling migrations' proven pattern and `npm test`/`npm run build`/`turbo typecheck`/`turbo test` for `apps/api`, not against a running Postgres instance.
