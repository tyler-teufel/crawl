#154: fixed `hotspot_score` (and, downstream, `is_trending`) sitting at 0 for every venue on the Supabase-native path, where the hourly node-cron recalculation job never runs because the Fastify API isn't deployed for this beta. Added `apps/api/drizzle/0006_hotspot_score_pg_cron.sql`, a migration that ports the scoring formula from `apps/api/src/jobs/recalculate-scores.ts` into a `SECURITY DEFINER` Postgres function (`public.recalculate_hotspot_scores()`) scheduled hourly via `pg_cron`, and seeds a non-zero baseline immediately on apply so Global Rankings and Explore aren't a flat, arbitrarily-ordered list of zeros on day one. `vote_count` is left untouched — that column belongs to #126's `cast_vote` RPC. The function pins `search_path = public, pg_temp` and revokes `EXECUTE` from `PUBLIC` (granting it only to the migration/cron-owning role) to close a temp-table-shadowing privilege-escalation path and an unauthenticated-PostgREST-RPC path caught in security review. Nothing has been applied to any live database; `pg_cron` availability on the project's Supabase plan, and the exact role `cron.schedule` runs jobs as, are both unverified.
